# E2E テスト設計（Playwright）

実ブラウザ（Chromium, iPhone 13 相当 390×844）から、**実バックエンド + 実 PostgreSQL** に対して操作する。
API はモックしない（通信エラーの異常系だけ `page.route` で意図的に壊す）。

## 実行方法

```bash
# 1. DB とバックエンドを起動（docker-compose か、ローカルの PostgreSQL + ./gradlew run）
docker-compose up -d postgres backend

# 2. フロントの依存とブラウザ（初回のみ）
cd frontend && npm install && npx playwright install chromium

# 3. 実行（Vite dev server は未起動なら自動起動。/api は :8080 へ proxy）
npm run test:e2e
npm run test:e2e:report      # HTML レポートを開く
```

| 環境変数 | 意味 |
|---|---|
| `E2E_BASE_URL` | フロントの URL（既定 `http://127.0.0.1:3000`） |
| `E2E_BROWSER` | Chromium 実行ファイルのパス（Playwright 管理外のブラウザを使うとき） |

バックエンドは `VAPID_PUBLIC_KEY` / `VAPID_PRIVATE_KEY` が無いと起動時に落ちる（`WebPushSenderImpl` の初期化）。
`npx web-push generate-vapid-keys` などで生成して環境変数に入れる。

## 設計方針

- **データは共有、名前で分離**: 1 つの DB を全テストで共有するので、テストごとに一意なメンバー名・タスク名を作り、件数ではなく「その名前が有る／無い」で検証する。`workers: 1` で直列実行。
- **セットアップは API、検証は UI**: 前提データ（メンバー登録、タスク定義、開始／完了）は `helpers.ts` の API ヘルパーで作り、画面操作と表示の検証に集中する。ログイン自体を検証するテスト以外は、アプリと同じ localStorage キーにトークンを注入してログイン済み状態から始める。
- **時刻は JST**: バックエンドは `Asia/Tokyo` で「今日」を決めるので、ブラウザも `timezoneId: 'Asia/Tokyo'` にし、ヘルパーの `todayJst()` と揃える。
- **通知モーダル**: 初回ログイン時に出る通知許可モーダルは、認証テスト以外では API で「今はしない」を回答済みにしてから開く。
- **異常系は 2 層**: UI が防いでいる操作（ボタン無効化など）と、UI を迂回して API を直接叩いたときにサーバーが拒否することの両方を確認する。

## 既知の仕様上の注意（テストで観測した挙動）

- **状態遷移違反は 500**: 二重開始などはバックエンドが `IllegalStateException` を投げ、`StatusPages` は `Throwable` として 500 で返す（`IllegalArgumentException` は 400）。テストは「拒否されること」と文言のみを検証している。
- **削除 → 実行のキャンセルは非同期**: タスク定義の削除イベントは Outbox テーブルに書かれ、10 秒間隔のスケジューラが当日分の実行を CANCELLED にする。A-STATE-5 は最大 30 秒ポーリングする。ホームから消えるのは即時（ダッシュボードのクエリが `is_deleted = false` で絞るため）。
- **メール検証の差**: クライアントは `^[^\s@]+@[^\s@]+\.[^\s@]+$`、サーバーは `^[A-Za-z0-9+_.-]+@[A-Za-z0-9.-]+$`（ASCII のみ）。日本語を含むアドレスはサーバーだけが弾く（A-VAL-8）。
- **登録の重複エラー文言**: サーバーは「既存のユーザ名と重複しています」を返すが、`AuthContext` は 400 を「この名前は既に使用されています」に置き換える。メンバー追加モーダルはサーバーの文言をそのまま出す。
- **メンバー追加のパスワード長**: モーダルはクライアント側で 8 文字以上、サーバー側は 5 文字以上。登録画面は 5 文字以上で揃っている。
- **エラーの自動消去**: メンバー画面のエラーは 5 秒で消えるので、表示直後に検証する。
- **開発モードの StrictMode**: 初回の取得 effect が 2 回走るため、「1 回だけ失敗させる」通信エラーの再現は成立しない。更新ボタンを押すまで失敗させ続ける。
- **`page.route` のパターン**: `**/api/...` 形式のグロブは Vite が配信する `/src/api/*.ts` にも一致してアプリの読み込みを止める。オリジン直後の `/api/` に固定した正規表現を使う。
- **カレンダーの表示上限**: 1 日のセルには 4 件までしか出ないので、当日分の検証はセルを開いた日別モーダルで行う。
